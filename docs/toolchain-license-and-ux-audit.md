# Toolchain licensing and product UX audit — 2026-09-27

Implementation and release work is tracked in GitHub issue #1.

## Decision

Continue toward a **bundled, versioned toolchain with complete public Android API definitions and matching framework resources**. Stop treating handwritten API signatures as the product strategy. The existing narrow worker remains a test harness until the broad replacement is verified.

The best user experience is to install the builder, finish one guided setup, describe an app, and receive a locally built app ready for Android's installation confirmation. Compiler licenses, source offers and notices belong in our release process and an offline licenses screen. Users should not have to obtain SDK JARs, select license interpretations, configure Termux or maintain dependencies manually.

There is a credible open source route. Applicable open source licenses already grant rights when their conditions are met; a special Google partnership is not inherently required for independently licensed AOSP components. The exact published SDK binary is a separate case: public availability and matching hashes establish identity, not the grant for every included component. The research is complete enough to select the route and define the remaining work; **it is not a completed release clearance or an acquired permission**. [Google's explanation of open source grants](https://opensource.google/documentation/reference/using/license), [AOSP licensing guidance](https://source.android.com/docs/setup/contribute/licenses).

## What changed our assessment

The API 36 revision 2 SDK has 6,227 class files. Its accompanying source archive has 4,161 Java files. A complete path/name comparison accounts for 6,222 classes; the five remaining entries are annotations. The source header groups include 2,679 Apache entries, 1,223 GPL-with-Classpath-Exception entries and smaller ICU, W3C, Chromium, SAX and XML Pull groups. Some generated or headerless files require parent-package/source mapping. This is a finite inventory, not a requirement to write Android's API declarations ourselves. A name match is not an API signature comparison or proof that a source rebuild reproduces the binary. The exact published artifacts are in [Google's r2 update](https://android.googlesource.com/platform/prebuilts/fullsdk/platforms/+/1b45636761b0dbab9f80779add8fc85ab94b80fb%5E%21/); the reproducible local scanner and results are in the API audit.

The whole JAR is 27,768,026 bytes (26.48 MiB), but its class entries have only 4,573,388 compressed payload bytes (4.36 MiB). Much of the remaining content is the framework resource table and images. These are measured archive sizes, **not** a promised replacement APK size or installed footprint. A classes-only library could reduce packaging and license scope, but still needs a separately licensed, version-matched resource input. A full JAR with established component rights is also acceptable; source rebuilding is a provenance choice, not a mandatory legal ritual.

The current debug controller is 8.66 MiB and worker 22.60 MiB. These local file measurements make bundling plausible, but no production-size or startup-performance result follows from them. No new APK was built or installed for this audit.

## How rights can be obtained

| Route | How we obtain the right | User experience | Assessment |
| --- | --- | --- | --- |
| Bundle independently licensed AOSP-derived API and resource artifacts | Identify applicable source/component grants, satisfy notices/source duties, and build or use a traceable artifact within those grants. Preserve required modifications/source materials. | Ready after installation; repeat builds work offline. | **Preferred engineering path.** No custom Google permission is inherently required where complete applicable open source grants exist. Source-build cost and public API/resource parity remain to be proved. |
| Bundle the exact official SDK artifact under established component grants | Complete the artifact-specific component/resource inventory and applicable section 3.5 case; meet each included component's terms. Seek clarification only for actual gaps. | Same good UX; exact API artifact already identified. | **Parallel route worth checking.** Could avoid a source rebuild. The current evidence does not clear the whole JAR and its resources. |
| Obtain additional written permission for the official SDK artifact | Ask the responsible rights holder to confirm allowed app-builder use, redistribution scope, updates and third-party exclusions. | Same good UX if suitable rights are granted. | A possible fallback. No public standard price, application or guaranteed response was established. Google cannot waive unrelated third-party duties. |
| Each user obtains Google's SDK directly on the phone | Verify the official download/use flow and applicable agreement; have the user accept the agreement themselves where required. | First-run transfer and failure recovery; cached builds later work offline. | **Not the preferred route.** It avoids some publisher redistribution but is not an established answer to the agreement's use restrictions. A compile-only API file must be distinguished from downloadable executable compiler code. |
| User imports an SDK from a computer | Establish permitted use and validate exact inputs. | Manual files, versions and licenses; often requires a second device. | Does not meet the intended normal UX. An import feature does not settle the underlying rights. |

The installed package agreement and current online terms are distinct records. Sections 3.2, 3.4 and 3.5 are materially relevant: SDK purpose, redistribution restrictions and the open source exception. **Do not turn the SDK's “another SDK” clause into a universal prohibition on AOSP.** For independent open source inputs, apply those licenses. For use of Google's SDK package in this product, whether that clause covers the proposed arrangement is an interpretation to resolve. A click-through, private alpha, sideload, public Git mirror or recompilation alone does not create missing rights. [Package-specific agreement](https://android.googlesource.com/platform/prebuilts/fullsdk/platforms/+/1b45636761b0dbab9f80779add8fc85ab94b80fb/android-36/package.xml), [current terms](https://developer.android.com/studio/terms).

The AOSP `prebuilts/sdk` licensing warning is a useful contact/routing pointer, but it is in a **different repository** from the exact `prebuilts/fullsdk/platforms` artifact. Its automatically aggregated license list can overinclude terms; it is not proof that every SDK class requires special permission. Ordinary component or directory-level licenses and applicable aggregate notices can be adequate evidence. The API audit records the precise remaining groups; a separate license certificate for every class is not a stated requirement.

For the ambiguous SDK-package route, the prepared inquiry asks for the exact component manifest and scope of permission. If existing grants suffice, document that basis and comply. If they do not, request written rights covering distribution in the worker and updates, or replace the affected artifact. A lawyer experienced in open source distribution can review the concrete packet; we do not need to ask them to investigate an unspecified compiler from scratch. That review is especially relevant to the package contract and corresponding-source/combination duties, not every ordinary Apache dependency. No paid engagement or external contact was initiated.

## Compiler and source delivery work

The separately tested source-built AAPT2 is preferable to the currently packaged opaque release. Its source revisions, patches and link inventory are known. This audit maps the 23 earlier header flags to generated inputs and component license evidence; they are not 23 independent permission requests. Remaining work includes NDK notice mapping and final notice packaging, then verification of the exact worker bytes. We do not need to negotiate a new license for a component already covered by a usable grant. The source and link records are in [the AAPT2 validation](validation/aapt2-source-build.md) and [input inventory](validation/aapt2-linked-inputs.md).

ECJ needs its EPL source-availability statement and corresponding source access; the official release publishes a source archive. The exact apksig JAR contains a full LICENSE that the current separate notice directory does not preserve. D8/R8's aggregate license includes reciprocal-license entries whose actual packaged content and conditions need resolution. The [compiler audit](research-compiler-license-path.md) gives each concrete action. Including a broad notice is helpful but does not satisfy missing source or relinking duties.

Keep the full applicable texts and a short component index available offline. Where source distribution is required, provide the matching covered source and build/modification material through a durable recipient-accessible release location. The current GitHub repository is private; an inaccessible private URL is not a usable source-delivery mechanism for public recipients. Required third-party source availability does not by itself mean every independently authored controller file or generated app must be relicensed. Review the exact combination and exceptions. Generated apps must include notices for libraries or runtime code actually copied into them; compile-only SDK definitions should stay out of their DEX.

## Define coverage so it is testable

The product target is **the complete public API surface of a selected SDK version**, with a managed route to supported library dependencies. It is not a manually selected list of Android methods. Compare a candidate against the reference's public/protected types, inheritance, fields and constant values, methods, generics and relevant annotations. Count equality alone cannot establish compatibility. Keep the selected SDK level recorded with each project. New Android APIs require a reviewed toolchain update; AOSP release timing and flags mean day-zero support cannot be promised automatically. [Android build version rules](https://developer.android.com/build), [AOSP release process](https://source.android.com/docs/setup/about/faqs).

Framework resources require the same care. The existing worker links against the running phone's `framework-res.apk`. The S23 fixture pass establishes that fixture on that device. It does not prove that an older phone can compile all newer-SDK resource attributes, or that different OEM resource tables reproduce the same compile SDK. Prefer a permitted canonical framework resource input for the selected SDK; if the device-resource route remains, demonstrate the supported version/OEM limits before promising parity. [AAPT2 resource linking](https://developer.android.com/tools/aapt2).

Current code also imposes unrelated limits: [`PatchApplier`](../controller/src/main/java/dev/smallwright/project/PatchApplier.java) allows seven files and a fixed flat Java package; [`BuildService`](../worker/src/main/java/dev/smallwright/worker/BuildService.java) compiles Java before resources, does not generate project `R` classes, rejects manifest permissions, and supplies D8 only generated-package classes. Therefore a new API JAR alone would still fail many ordinary app requests. Expand these paths with tests while retaining bounded inputs, authenticated Binder, per-project keys and no generated-code execution in the controller.

AndroidX, Compose, Google Play services, Firebase and other libraries are separate artifacts and sometimes separate service agreements. Their AARs may require resource/manifest merging, transitive dependencies, Kotlin support, native libraries or code generation. Add managed dependency support in tested stages; automatically choose and pin supported versions so users do not maintain Maven coordinates. Keep a machine-readable capability description for generation and validate imports/dependencies before a long build. Unsupported features should produce an early explanation with a usable alternative, not mysterious disabled buttons. This is a failure-handling requirement, not a substitute for broadening support. [AAR contents and integration](https://developer.android.com/studio/projects/android-library), [dependency management](https://developer.android.com/build/dependencies), [Play services setup](https://developers.google.com/android/guides/setup).

## Best achievable user journey

1. **Install and become ready.** Bundle the tested compiler and default platform inputs through the app's signed distribution channel. In the current two-APK design, guide the companion-worker installation and verify signer/version compatibility. Run a small local compiler self-test before accepting the first generation request. Show a specific retry action if setup fails. Do not expose SDK paths or terminals to ordinary users.
2. **Create.** The controller selects the project's tested toolchain and dependency versions. It checks whether the requested feature needs a permission, a service account, or an unsupported build feature before promising a result. Cloud inference remains clearly identified; cached builds and the local generated app can work without a connection when their own features permit it.
3. **Build.** Show editing, resource processing, compiling and signing progress with cancellation. A failed compiler leaves the project editable and exposes diagnostics/repair. A global disabled state must have a reason and recovery action. No paid inference should be spent retrying a known absent platform library.
4. **Install and test.** Present a clear Install action, the relevant permissions and Android's confirmation. Preserve the project package/signing identity across updates and test app-data continuity. Platform consent is part of the experience and cannot honestly be promised away.
5. **Update tooling.** Use signed harness updates for executable compilers. Retain compatible project toolchain versions or perform a checked migration with a recoverable project snapshot. Do not silently break existing projects by replacing a compile SDK or library. Recovery need not mean Android APK version downgrades; a later signed release can restore earlier compiler behavior.

One APK with an `isolatedProcess` service was tested on the A33 on 2026-11-03. UID separation, network denial and native AAPT2 execution worked, but there is no writable scratch and passed descriptors cannot be reopened by path, so AAPT2 cannot build there ([record](validation/isolated-process-a33-20261103.md)). A normal same-UID secondary process is not equivalent. [Android service isolation attributes](https://developer.android.com/guide/topics/manifest/service-element).

## Distribution and installation constraints that affect UX

**Play approval is separate from component licenses.** The install permission policy does not explicitly list an IDE among its permitted examples; executable-download and policy-coverage rules also need evaluation for this exact app. A source-only/compile-data download is not automatically a runtime dynamic load, but this distinction is not blanket Play approval. Use the prepared product-specific inquiry and a truthful declaration if pursuing Play. Start device evaluation through a direct signed distribution only after the applicable redistribution conditions are met. Direct delivery still requires Android's normal installation flow. [Play install permission](https://support.google.com/googleplay/android-developer/answer/12085295?hl=en), [device/network policy](https://support.google.com/googleplay/android-developer/answer/16559646?hl=en).

**Developer verification may create future onboarding work for generated apps.** As checked on 2026-09-27, the current official rollout guide limits September 30 enforcement to named participating stores in Brazil, Indonesia, Singapore and Thailand, with broader global/all-app expansion planned for 2027. The FAQ explicitly says direct sideloading is not covered by that initial deadline. Older paragraphs imply a broader September requirement; use the dated current clarification. This is not evidence of a new block on this S23 today. [Current rollout](https://developer.android.com/developer-verification/guides), [FAQ clarification](https://developer.android.com/developer-verification/guides/faq).

For that later expansion, registering our controller/worker cannot be assumed to register each user's distinct generated package/key. Options documented by Google include verified developer registration, limited distribution, and advanced flow for unregistered apps. Advanced flow has a one-time one-day wait and user security steps, so it cannot support an unconditional instant first-install promise. Limited distribution supports up to 20 authorized devices but adds account/device approval work. [Advanced-flow FAQ](https://developer.android.com/developer-verification/guides/faq), [limited-distribution guide](https://developer.android.com/developer-verification/guides/limited-distribution).

The Console API can register a previously unseen package using its public certificate; some existing-package cases require a signed challenge APK upload. Its guide presents server-to-server integration and user OAuth flows. A direct Android-client flow, quotas, account ownership and personal-app-builder treatment still need confirmation. The Status API checks registration; it does not register an app. No backend, embedded service-account secret, shared generated-app signing key, or APK upload is authorized by this audit. The existing cloud-inference-only scope would need an explicit decision before adding registration network calls. Prefer a supported flow using public metadata if available, and keep private keys on the phone. [Console API](https://developer.android.com/developer-verification/guides/developer-console-api), [Status API](https://developer.android.com/developer-verification/guides/check-registration-status).

## Ordered implementation and release gates

| Order | Concrete result | Acceptance evidence |
| --- | --- | --- |
| 1 | A complete permitted API/resource input set for one SDK level | Pinned component licenses/notices and necessary source delivery; resolve the finite source/annotation/resource gaps. Use existing grants where sufficient; send the prepared inquiry only for material ambiguities. No missing APIs silently removed. |
| 2 | A broad compiler proof | Reference/candidate API signature comparison; real host compile comparisons; phone tests using collections, notes, SQLite, XML layouts and generated `R`, threading, files and version-aware API use. Include invalid-source tests and prove SDK classes are absent from generated DEX. Record resource compatibility and compiler/language limits. |
| 3 | A distributable bundled worker | Finish source-built AAPT2 notices and ECJ/R8/apksig duties; verify final APK contents, separate UID/network denial, ABI/page size and physical build/install/update tests. |
| 4 | Ordinary app project support | Tested project package selection, directory/resource handling, permission review and diagnostics. Then managed library/AAR support and Kotlin/Compose only when their real pipeline works on the phone. |
| 5 | Guided onboarding and updates | Fresh-device setup, interrupted setup, insufficient storage, lost network, cancel/retry, old-project rebuild and generated-app data-retention tests. Decide one-APK isolation only after proof. |
| 6 | Public distribution | Resolve store policy for the chosen channel and test registration/install UX under the applicable verification rollout. Do not market unrestricted instant installation before this gate. |

There is no justified effort estimate for the full source rebuild or broader library pipeline yet. Gate 1 can proceed as a bounded inventory/provenance task, while a legal reviewer or rights holder addresses narrowly stated ambiguities. If that route fails, decide between written rights for the SDK artifact and another permitted equivalent. More handwritten platform API patches do not satisfy the user's requested product.

## Checks performed and limits

- Read the implementation plan, current status, exact tool manifest and existing source/link/provenance audits; inspected the live build's source/resource/policy paths.
- Independently rechecked the local SDK class/source counts, unmatched annotation names, header categories, exact SDK blob hash and artifact sizes. The SDK memo contains the repeatable scanner. Rechecked the apksig JAR's embedded LICENSE hash against the compiler research.
- Reviewed primary SDK/OSS license texts, official executable and Play rules, and current developer-verification documentation; corrected initial research that conflated source-data JARs with runtime loading, recommended more handwritten stubs, or applied the SDK contract universally to AOSP.
- Ran documentation/link/whitespace checks recorded in `STATUS.md`. No new app runtime pass, phone measurement, legal opinion, rights-holder answer, Play approval or redistribution authorization is claimed. No external inquiry was sent and no paid/cloud resource was created.

The audit covers the compiler/API distribution decision and resulting product UX. It is not a full review of future AI-provider contracts, privacy law, every possible third-party SDK, trademarks, patents or app-store eligibility in every jurisdiction. Those become specific checks when the product selects the relevant feature or distribution channel.
