This is an evidence and closure plan for a future distributable controller/worker pair, not a legal approval or a change to the current APKs. The current worker still embeds the opaque `lzhiyong/android-sdk-tools` 35.0.2 AAPT2 binary. The cleaner route is the separately built Android 16 ARM64 AAPT2 candidate, **after** its remaining license and notice work is closed. No Google partnership, custom permission, or private license is presumed: applicable open-source grants are the route. The SDK agreement itself distinguishes its default no-redistribution rule from components governed by open-source licenses ([Android SDK terms, §§3.4–3.5](https://developer.android.com/studio/terms)).

## Finish the source-built AAPT2 rights record

1. **Fix the release identity.** Choose one fresh, pinned ARM64 candidate build; record its exact source/submodule revisions, local patch hashes, NDK r28c and dependency versions, build command, link-map hash and final stripped ELF SHA-256 in `toolchain/manifest.json` and the release notes. Move the worker input to this candidate only after the audit, then verify the exact embedded APK asset hash. The two clean/replay binaries are functionally tested but have different hashes across output directories, so describe source reproducibility, not byte-for-byte reproducibility. Retire the opaque 35.0.2 AAPT2 from a distributable build; its source-to-release mapping is still missing.
2. **Map selected code by component, then follow material exceptions.** Use `toolchain/aapt2-source-compat/link-members.json` and the retained `lld` map to group the 399 selected archive objects and ten direct AAPT2 command objects by pinned source component. The selected AOSP, Abseil and other third-party `.cc`/`.c` mapping is substantially documented in [the linked-input inventory](validation/aapt2-linked-inputs.md). Recheck the duplicate `Util.cpp.o` label as two AOSP source files. For the generated AAPT2/protobuf objects, link each to its pinned `.proto` and generator. Inspect *included headers that contribute inline/templates or copied definitions* for different terms, especially the 23 first-pass unmarked header-like inputs; an absent per-file marker calls for parent-directory/build metadata review, not automatic rejection. Record reasonable evidence and any material exceptions. Do not require a theoretical file-by-file proof for Android system `.so` libraries that are not distributed in the APK.
3. **Resolve NDK static code specifically.** The link includes four NDK static archives (110 selected member labels) and `crtbegin_dynamic.o`/`crtend_android.o`. Match their installed r28c paths to the relevant `NOTICE.toolchain`, LLVM prebuilt `NOTICE`, sysroot `NOTICE`, and any component-specific license sections. The current tracked NDK notices are broad and include unrelated host tools; they may be used as an aggregate bundle if they cover the selected code, with the record explaining that mapping. Check compiler builtins, unwind and libc++abi as well as libc++. The Android [NDK runtime guide](https://developer.android.com/ndk/guides/cpp-support) supports normal runtime packaging; it does not replace the exact notice determination.
4. **Collect the pinned component notices, not similarly named old-revision substitutes.** The linked pinned AOSP source trees contain `base/NOTICE`, `base/libs/androidfw/NOTICE`, `core/libcutils/NOTICE`, `core/libutils/NOTICE`, `incremental_delivery/incfs/NOTICE`, `libbase/NOTICE` and `logging/liblog/NOTICE`; record their source commit and SHA-256, copy applicable text, and include the wrapper license and existing pinned third-party notices. `libziparchive` has no checkout-root notice; its selected source files have Apache headers, so inspect relevant included headers and provide an Apache-2.0 copy and attribution as applicable. Confirm the chosen artifact's link map still excludes GoogleTest and zlib static archives before treating them as build inputs only. The existing `aapt2-aosp/` files include notices from **other** revisions and cannot silently stand in for the source-built candidate.
5. **Document modifications.** Ship or offer the exact corresponding wrapper/AOSP patch set and dependency source route, preserving source headers and marking modified files as Apache-2.0 §4 requires. Record the local Aconfig shim's behavior and the IncFS compatibility guard as runtime limitations alongside the source offer; they are not license defects by themselves. Keep source acquisition reproducible without host credentials. A release build must recheck the actual link map after any compiler or source change.

### What the pinned R8 JAR reveals

The exact `toolchain/input/r8-8.13.23.jar` is SHA-256 `e3cdcb003d9beca956209ad6b9e9df31f26b732bfaed9c7c8674e903ca9f3b81`. Its `r8-version.properties` names source revision `5fa61e42c2aca157e391442fd89bbec558c83b97`. ZIP inspection found 7,162 classes, all under `com/android/tools/r8/`; there are no classes in original `gnu/trove`, `it/unimi/dsi/fastutil`, JAXB, or `org/glassfish` namespaces. There is an obfuscated class containing a `fastutil` diagnostic/string. **This neither proves embedded fastutil nor excludes relocated Trove/JAXB.**

At that [exact R8 revision](https://r8.googlesource.com/r8/+/5fa61e42c2aca157e391442fd89bbec558c83b97/), the [main Gradle build](https://r8.googlesource.com/r8/+/5fa61e42c2aca157e391442fd89bbec558c83b97/d8_r8/main/build.gradle.kts) assembles a `deps.jar` from the main and resource-shrinker dependency JARs, generates the consolidated `LICENSE` from the full `LIBRARY-LICENSE`, then runs `r8WithRelocatedDeps` to produce `r8.jar`. Its license generation checks that runtime dependencies are *mentioned* in `LIBRARY-LICENSE`; it appends that full list, not a filtered list of only runtime artifacts. The [pinned version declarations](https://r8.googlesource.com/r8/+/5fa61e42c2aca157e391442fd89bbec558c83b97/d8_r8/commonBuildSrc/src/main/kotlin/DependenciesPlugin.kt) show direct fastutil `7.2.1`, ASM `9.8`, Gson `2.10.1`, Guava `32.1.2-jre`, Kotlin `1.9.20`, Kotlin metadata `2.2.10`, and protobuf `3.19.3`. The bundled `LICENSE` uses `+` or no version for its dependency entries, including LGPL Trove4J and CDDL/GPL JAXB; it **does not identify their resolved versions**. A different local Gradle distribution's Trove JAR must not be treated as R8's dependency.

Practical closure: obtain or generate the SBOM and resolved dependency graph **for that exact R8 revision/artifact**, plus the dependency archive identified by the revision's `third_party/dependencies.tar.gz.sha1` if needed. Match class provenance before and after relocation using the upstream `deps.jar`/`r8.jar` build inputs or publisher SBOM; exact namespace search after obfuscation is insufficient. For any included LGPL Trove4J or CDDL/GPL JAXB code, identify its version and chosen license branch, publish the matching source and required texts alongside the APK, and supply a workable replacement/relink route where LGPL §6 applies. A D8 release process that permanently shrinks/obfuscates an LGPL library without a workable replacement route may need that code excluded or another compliant compiler artifact. This is a finite release task, not a claim that all listed reciprocal dependencies are present or that the current JAR is cleared.

## Delivery and user experience

Ship the required notices **with the APK that contains each component** and make them easy to reach offline from an ordinary **About → Open-source licenses** entry. A concise component index should name AAPT2, ECJ, D8/R8, apksig and controller dependencies, versions, exact source URLs, license families, modification notes and full applicable texts. A normal aggregate NOTICE is acceptable where it actually covers linked content; users should not face 399 object rows. The generated counter APK does not contain the compiler, so compiler notices belong in the controller/worker distribution, not in every generated app. Verify final APK entries and hashes against the release bill of materials, not just the repository's notice files.

For ECJ, place the exact `ecjsrc-4.12.jar` source link and EPL source-availability statement in that offline entry and release page. For D8/R8, retain the complete pinned `LICENSE` while resolving any actually embedded reciprocal libraries. For apksig, add its exact embedded `LICENSE`, which the current notice index omits. Present the legal material without interrupting the source-edit/build/install flow. The controller and worker may each include a common aggregate bundle for convenience, though the release check should know which code each APK actually contains.

**Release gate:** after the above, a reviewer can match each shippable APK's compiler binaries and Java libraries to pinned source/artifact hashes, material license grants, applicable notices/source offers and offline access. If any genuinely included component lacks a redistribution grant or required source/relinking path, replace it or resolve that condition before sharing APKs. The currently installed/locally tested APKs and the clean-source candidate do **not** yet pass this distribution gate.
