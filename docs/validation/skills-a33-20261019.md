# Skills from GitHub on the Galaxy A33, 2026-10-19

Issue #57 (parent #53): the person adds skills from a GitHub link in Settings,
and the builder uses them during a run. Decision record:
`docs/adr/0005-skills-are-text.md`. Glossary: "Skill".

## What changed

- `skills/`: `GitHubLink` turns a repository, `tree/<ref>/<folder>` or
  `blob/<ref>/<folder>/SKILL.md` link into GitHub API and raw addresses.
  `GitHubSkills` asks the API for the commit (`commits/<ref>`, `Accept:
  application/vnd.github.sha`) and the recursive tree, then downloads only each
  skill's `.md` files from raw.githubusercontent.com at that commit and checks
  each against its git blob SHA-1. `SkillFile` parses the frontmatter (name and
  description required, name per the format, description at most 1024
  characters, `disable-model-invocation`). `SkillStore` keeps skills in the
  controller's files (`files/skills/`), one new folder per added skill, with an
  index of on/off.
- Limits: 64 KB per file, 512 KB per skill, 100 skills per link. A skill outside
  them, or one that does not parse, is skipped with a plain reason.
- `net/HttpsDownload`: the bounded HTTPS GET that `MavenRepositories.fetch` had,
  moved unchanged (same timeouts, no redirects, same messages, same 404/410
  handling) so skills use the same code. `MavenRepositories` now calls it; the
  library tests are unchanged. `MavenFixture` gained `status(...)` for GitHub's
  403/422 answers; existing fixture behaviour is unchanged.
- At the tap on Send (`RunSkills.atSend`, inside `ContextPreviewGate`): the
  skills that are on and the model may start are listed by name and
  description in the first request with a `skills_note`. A message that starts
  with `/name` adds that skill's `SKILL.md` as `skill_in_use` and shows the
  step "Using skill name". An unknown or switched-off `/name` is refused before
  anything is sent. The preview and the approved payload must match, so a
  skill changed between them is refused like any other context change.
- New tool `read_skill(name, file?)`: reads only skills captured at the tap and
  only files each one holds. Shows "Read skill name".
- Settings, new "skills" section: GitHub link, "Add skills", the found skills
  with `[x]` boxes, "Add N skills", the added skills with `[x]` on/off and
  Remove, and the note. Same-name skills ask "Yes, replace them" first. Skills
  only the person can start say "Starts only when you begin a message with
  /name". The status line scrolls into view while finding and adding.
- `StepSummaries` (#54): "Using skill" and "Read skill" count as skills, not
  files ("Used skill grill-me, read skill grilling").

## Review fixes (commit ffc8d6e)

An independent review found seven defects; each is fixed with host tests.

- Skill files and the list are fsynced before their rename. A damaged list no
  longer blocks Send: a message without `/name` goes with no skills, and
  Settings shows "The list of skills is damaged…" with "Remove all skills".
- A skill file whose size differs from the recorded size is never sent or
  read (an emptied `SKILL.md` is refused).
- Adding writes the files before taking the store lock; toggle and remove run
  off the main thread; toggle flips in one locked step.
- The file list is capped at 2 MB, and a link's skills at 8 MB, checked from
  the tree's sizes before any download and again while downloading.
- A person-only skill started with `/name` earlier in the chat is offered and
  readable on later messages (taken from the chat's own messages at Send, so
  the preview matches what is sent).
- The descriptions sent are capped at 16 KB; over that, Send is refused with
  "Too many skills are on. Turn some off in Settings."
