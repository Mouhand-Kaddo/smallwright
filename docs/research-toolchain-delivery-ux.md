# Phone-local toolchain delivery and UX research

Research checked 2026-09-27. This is an engineering recommendation, not redistribution clearance or a prediction of Play review. It concerns the two-APK controller and separate-UID worker in [the implementation plan](IMPLEMENTATION_PLAN.md). The current worker builds Java/XML on the S23 Ultra without an SDK `android.jar`, using authored compile stubs and the device's `framework-res.apk`. Its packaged AAPT2 still has an open redistribution/notice gate, and generated-app runtime/update of the latest user source awaits explicit physical installation; see [STATUS](STATUS.md) and [the AAPT2 audit](toolchain-redistribution-audit.md).

## Evidence that constrains delivery

- **SDK terms apply to SDK artifacts, regardless of installer UI.** Section 3.2 limits use to developing apps for compatible Android implementations and bars using the SDK to develop another SDK. Section 3.4 restricts copying and redistribution except as required by third-party licenses. Section 3.5 says open-source SDK components follow their own licenses. A user click-through or a download initiated on the phone does not, by itself, settle whether this builder's SDK use or redistribution is permitted. Component-specific provenance and terms must be resolved. [Android SDK License Agreement](https://developer.android.com/studio/terms). Google's `sdkmanager` documentation describes per-package license acceptance for ordinary SDK installation; it does not grant a builder permission to redistribute the packages or convert host build tools into Android executables. [SDK Manager](https://developer.android.com/tools/sdkmanager).
- **APK packaging is the dependable native-executable route for the selected target.** Android's API 29+ behavior page says untrusted apps cannot `execve()` files in their writable app home directory and says apps should load binary code embedded in the APK. Downloading an ELF into worker-private storage is therefore not a workable executable update path for this modern-target worker. The current worker invokes packaged `libaapt2_exec.so` from `nativeLibraryDir`; any replacement needs device execution tests under the same target and ABI. [Android 10 executable restriction](https://developer.android.com/about/versions/10/behavior-changes-10#execute-permission). Native code also needs 16 KiB page compatibility on capable Android 15+ devices; Android 16 compatibility mode is not a substitute for aligned builds. [16 KiB guidance](https://developer.android.com/guide/practices/page-sizes), [Android 16 behavior](https://developer.android.com/about/versions/16/behavior-changes-all).
- **Dynamic Java code has a distinct restriction.** Apps targeting API 34+ must mark dynamically loaded DEX/JAR/APK files read-only before writing them. That rule concerns *loading code into a process*. A platform API JAR read solely by ECJ as compile definitions is a separate input case; it does not automatically trigger the dynamic-code-loading rule. Its SDK license, source/provenance, integrity, and any applicable Play interpretation still need review. Keep compiler execution fixed in the signed worker, and generated-app execution in separately installed packages. [Android 14 dynamic-code behavior](https://developer.android.com/about/versions/14/behavior-changes-14#safer-dynamic-code-loading), [Android dynamic-code security guidance](https://developer.android.com/privacy-and-security/risks/dynamic-code-loading), [SDK terms](https://developer.android.com/studio/terms).
- **Play policy is an additional distribution gate.** A Play-distributed app may not self-update outside Play or download executable DEX, JAR, or `.so` code from elsewhere. The same policy prohibits installing another app without prior user consent. Whether locally compiled generated APKs, source imports, and a builder's install flow are accepted needs review of the exact implementation; the text does not grant a blanket IDE exception. [Play Device and Network Abuse](https://support.google.com/googleplay/android-developer/answer/16559646?hl=en). `REQUEST_INSTALL_PACKAGES` is restricted: Play requires sending/receiving packages and user-initiated installation as core functionality, a declaration, and an eligible use. Its published examples do not explicitly name IDEs. Do not assume a builder listing qualifies. [Play install-package permission](https://support.google.com/googleplay/android-developer/answer/12085295?hl=en). The broader [Policy Coverage](https://support.google.com/googleplay/android-developer/answer/10146128?hl=en) language about apps that let users install other apps is a further reason for a product-specific Play review; this note makes no eligibility claim.
- **User approval is a real platform step.** `PackageInstaller.SessionParams.USER_ACTION_REQUIRED` yields `STATUS_PENDING_USER_ACTION`, and the system supplies an intent for the confirmation UI. Use that path for each generated-app installation/update and reconcile actual package state after interruption. [SessionParams](https://developer.android.com/reference/android/content/pm/PackageInstaller.SessionParams#setRequireUserAction(int)), [PackageInstaller status](https://developer.android.com/reference/android/content/pm/PackageInstaller#STATUS_PENDING_USER_ACTION). For any later Play release, the current submission requirement for ordinary phone apps is target API 36+ as of 2026-08-31. [Play target API](https://developer.android.com/google/play/requirements/target-sdk).

## Delivery choices

| Choice | Onboarding and offline result | Decision and constraint |
| --- | --- | --- |
| Bundle a pinned, reviewed ARM64 compiler in the signed worker APK | One disclosed worker install after the controller; builds work offline once both are installed. Publisher can update worker through the same signed app channel. | **Recommended for the alpha after the AAPT2 audit closes.** Keep checksums, component/link notices, ABI/page-size tests, and rollback-safe harness updates. The current source-built AAPT2 candidate has phone execution evidence, but its linked-object notice map remains incomplete. [Local audit](toolchain-redistribution-audit.md); [Android executable restriction](https://developer.android.com/about/versions/10/behavior-changes-10#execute-permission). |
| Download executable compilers/tools directly on the phone during onboarding | Smaller initial APK, but a large first-run transfer, failure/retry state, no first-run offline build, and version drift unless pinned and verified. | **Do not use as a shortcut around licensing or OS execution rules.** Per-user SDK license acceptance does not resolve the builder's section 3.2 purpose or section 3.4 redistribution questions. A downloaded native executable in app-private storage encounters W^X; a Play edition cannot fetch executable compiler code outside Play. [SDK terms](https://developer.android.com/studio/terms); [Android 10 restriction](https://developer.android.com/about/versions/10/behavior-changes-10#execute-permission); [Play policy](https://support.google.com/googleplay/android-developer/answer/16559646?hl=en). |
| Obtain a full platform API JAR as a **compile-only input**, bundled or downloaded on-device | Bundling gives immediate offline builds if redistribution is permitted; a phone download adds setup and connectivity but can be cached for later offline builds. | **Investigate separately from executable-tool delivery.** ECJ reading class definitions as data is not `execve()` or dynamic class loading. A click-through alone does not establish SDK-use or redistribution rights. Pin the exact artifact, verify bytes, ensure no class loading/execution, and test API-coverage parity on phone. A future Play edition needs a specific review because its policy names JARs as an example of executable code without distinguishing compile-only use. [SDK terms](https://developer.android.com/studio/terms); [Android 10 restriction](https://developer.android.com/about/versions/10/behavior-changes-10#execute-permission); [Android 14 dynamic-code behavior](https://developer.android.com/about/versions/14/behavior-changes-14#safer-dynamic-code-loading); [Play policy](https://support.google.com/googleplay/android-developer/answer/16559646?hl=en). |
| Let a user import pinned compile inputs from another device | Avoids an in-app downloader, but adds setup and transfers provenance, version, license and storage questions to the user. | **Fallback, not default onboarding.** Parse and verify known JAR/AAR inputs inside the restricted worker without executing them. Import alone does not defeat the separate-UID boundary; loading imported code as a plugin or annotation processor would change that boundary and is outside scope. Review rights and full integration before exposing a library as supported. [SDK terms](https://developer.android.com/studio/terms); [Android library and AAR anatomy](https://developer.android.com/studio/projects/android-library). |

**Interpretation:** For this product's offline and low-friction goal, a bigger two-APK first install with the reviewed executable compiler is preferable to a small shell that must download executable tools before its first build. Full platform API definitions are a separate decision: bundle a permitted artifact for immediate offline use, or make a verified first-run phone download explicit and cache it for later offline use if the terms allow that route. Neither path can be represented as seamless until the license and phone parity gates pass. The two APKs must keep the worker's distinct UID and lack of Internet permission. A single-APK isolated service can be studied later only after equivalent confinement and compiler tests. [Local audit](toolchain-redistribution-audit.md); [SDK terms](https://developer.android.com/studio/terms); [Android service process attributes](https://developer.android.com/guide/topics/manifest/service-element).

## API breadth and libraries

`android.jar` contains Android framework compile signatures; it is not an AndroidX, Material, or Google Play services dependency catalog. AndroidX libraries ship separately from the OS and are officially tested with Gradle and Android Gradle Plugin, not this project's fixed ECJ/AAPT2/D8 pipeline. [AndroidX overview](https://developer.android.com/jetpack/androidx.html), [AndroidX releases](https://developer.android.com/jetpack/androidx/versions). An AAR can contain `classes.jar`, resources, a manifest, embedded JARs, native libraries and consumer ProGuard rules. Directly importing one can also require manual management of transitive dependencies. The fixed pipeline would need explicit resource/manifest merging, classpath/dex handling, native ABI checks, dependency resolution, shrinker rules where applicable, and license/provenance review for **each curated artifact**. [Android library and AAR anatomy](https://developer.android.com/studio/projects/android-library).

There are concrete product limits beyond the current compile stubs. [`PatchApplier`](../controller/src/main/java/dev/smallwright/project/PatchApplier.java) caps a project at seven source files. [`BuildService`](../worker/src/main/java/dev/smallwright/worker/BuildService.java) accepts only a fixed `dev.smallwright.generated.counter` package, flat Java files in that package, and XML under `res/layout` or `res/values`; it rejects manifest permissions. Its build runs ECJ before AAPT2 and does not request AAPT2 Java `R` output, while D8 receives only generated package class files. **Inference from this implementation:** importing a complete `android.jar` alone would not enable ordinary resource-ID based apps, arbitrary packages, permissioned features, or AAR dependencies. Each requires a separately tested build/policy slice.

Google Play services is yet another layer: its client SDK is added as a dependency and communicates at runtime with the installed Google Play services app; devices without Play services need a missing-service path. It cannot be assumed from `android.jar` or the presence of a Samsung phone. [Google Play services overview](https://developers.google.com/android/guides/overview), [setup](https://developers.google.com/android/guides/setup). Google says developers are responsible for included open-source notices; documentation page licenses are not a license for every Maven artifact. Review exact AAR/POM terms, transitive artifacts, data practices and any service terms before adding one. [Google OSS notice guidance](https://developers.google.com/android/guides/opensource), [Play services data disclosure](https://developers.google.com/android/guides/play-data-disclosure).

**Recommendation:** Treat the authored signatures as a temporary first-APK bridge, not the product's API strategy. Resolve the rights and provenance of a **complete compile-only platform API library** for one pinned SDK version, then replace the handwritten signatures and run phone-local parity tests across the public framework API surface, including source compilation and representative runtime behavior. A broad API definition set does not by itself complete the builder: add `R` generation, resource references, bounded package/manifest policy, and library packaging with real phone tests. State support by *build feature and dependency version* while those integrations mature; do not quietly imply that every API or AAR already works. Expand a predictable, audited set of AndroidX/Google libraries as their complete dependency, resource, native, terms, and runtime paths pass—not as a permanent narrow catalog. Continue rejecting model-provided Gradle files, plugins, annotation processors and unreviewed Maven coordinates. [Local status](STATUS.md); [AAR anatomy](https://developer.android.com/studio/projects/android-library); [AndroidX overview](https://developer.android.com/jetpack/androidx.html); [SDK terms](https://developer.android.com/studio/terms).

## Concrete onboarding and update flow

1. **Before release:** close AAPT2 linked-object provenance/notices; select the exact ARM64 compiler bytes and checksum; test 4 KiB/16 KiB page compatibility and current target; pin controller/worker versions and signing identities. Current source-built candidate is useful evidence, not release clearance. [Local audit](toolchain-redistribution-audit.md); [16 KiB guidance](https://developer.android.com/guide/practices/page-sizes).
2. **First run:** explain the companion worker and its separate UID/no-Internet role, the installed bytes/storage cost, cloud model context, and the fact that builds are phone-local. Check whether the compatible signed worker is present; guide an explicit install if missing. If the rights-cleared platform API input uses an on-phone download, show its size, terms, checksum verification and retry/offline state before claiming setup is complete. Then run a no-credential local compiler self-test and record its actual result. [Android service process attributes](https://developer.android.com/guide/topics/manifest/service-element); [SDK terms](https://developer.android.com/studio/terms); [PackageInstaller status](https://developer.android.com/reference/android/content/pm/PackageInstaller#STATUS_PENDING_USER_ACTION).
3. **Build and install:** allow source edits and cached builds offline; keep cloud inference separately identified as requiring network. Show precise compile errors, signed APK package/version/permissions, and an Install action that leads to Android's confirmation. Never imply that compilation equals installation or that installation equals a functional pass. [SessionParams](https://developer.android.com/reference/android/content/pm/PackageInstaller.SessionParams#setRequireUserAction(int)); [Local plan](IMPLEMENTATION_PLAN.md).
4. **Updates:** deliver controller and worker as signed APK updates through their chosen distribution channel; verify version/signature compatibility before a build. Keep the trusted toolchain inside the updated worker rather than fetching executable patches. Generated-app updates keep their own per-project signer, stable package name, increasing version code, explicit user confirmation and data migration tests. For a prospective Play edition, use Play's update mechanism for the harness and separately review the generated-app install model. [Play policy](https://support.google.com/googleplay/android-developer/answer/16559646?hl=en); [App signing](https://developer.android.com/studio/publish/app-signing); [Local plan](IMPLEMENTATION_PLAN.md).

**Open decision for any public distribution:** the exact compiler/library redistribution basis and Play eligibility are unresolved. Direct private alpha is the immediate test channel only after the license gate closes; it does not bypass Android's execution rules or installation consent. Developer verification and package registration are a separate distribution review and should be checked against the current rollout before widening delivery. [SDK terms](https://developer.android.com/studio/terms); [Play policy](https://support.google.com/googleplay/android-developer/answer/16559646?hl=en); [Android developer verification](https://developer.android.com/developer-verification).
